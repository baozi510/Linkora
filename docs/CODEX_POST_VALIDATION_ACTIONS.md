## 2. Required correction A — MPV error stream is not a fatal-error contract

### Finding

Current Linkora code:

`entry/src/main/ets/playback/MpvPlaybackPort.ets`

subscribes to:

```text
player.stream.error
```

and immediately treats every value as a fatal playback error.

Upstream `mpv-ohos/mpv-arkts` currently implements `stream.error` from its log callback:

```text
if (level == "error") {
  this.stream.error.add(msg)
}
```

Therefore this stream means:

```text
mpv log message whose severity == error
```

not:

```text
structured fatal playback failure
```

mpv can emit error-level log lines for recoverable situations. Treating every such line as fatal can incorrectly fail prepare or tear down an otherwise playable session.

### Required change

Do not call `failPrepare()` or `observer.onError()` solely because `player.stream.error` emitted a log line.

Recommended first implementation:

- retain the latest error-level log line only as diagnostics;
- during prepare, use FILE_LOADED as success and the existing prepare timeout as failure;
- if prepare times out, include the latest error-level log text in the diagnostic detail;
- after prepare, error-level log messages must not independently transition the unified player to ERROR.

Do not invent a structured mpv fatal event if the wrapper does not expose one.

If the wrapper later exposes an actual end-file/error reason, integrate that separately.

### Required tests

Add deterministic tests proving:

1. an MPV error-level log before FILE_LOADED does not immediately fail the candidate;
2. FILE_LOADED after such a log still allows prepare to succeed;
3. prepare timeout can include the last error log as diagnostic detail;
4. a post-prepare error-level log does not automatically tear down playback.

Do not claim runtime semantics are fully verified until arm64 device testing.

## 3. Required correction B — Surface size is not connected from UI to PlaybackEngine

### Finding

Phase 7 added:

- `PlaybackEngine.setSurfaceSize()`
- `PlaybackPort.setSurfaceSize()`
- MPV property `ohos-surface-size`

but the current UI path does not actually forward area changes.

Current `PlayerPage`:

```text
onAreaChange
  -> surfaceWidth/surfaceHeight local fields only
```

`PlayerFeatureController` currently has no public `setSurfaceSize()` method.

Therefore the real path is incomplete:

```text
PlayerPage
  X
PlayerFeatureController
  X
PlaybackEngine.setSurfaceSize
  ->
AdaptivePlaybackPort
  ->
MpvPlaybackPort
```

### Required change

Add:

```text
PlayerFeatureController.setSurfaceSize(width, height)
  -> PlaybackEngine.setSurfaceSize(width, height)
```

In `PlayerPage`:

- call the controller method from `onAreaChange`;
- also send the currently known size around surface attachment so ordering does not matter.

The engine already stores width/height before backend creation, so preserve that design.

### Required tests

Add tests proving:

- surface size set before open reaches a newly created backend;
- surface size change after open reaches the active backend;
- width/height are clamped/normalized as intended;
- surface detach/reopen does not reuse stale backend events.

## 4. Required correction C — BT.2020 alone is not HDR

### Finding

Current `PortVideoInfo.hdrLabel()` returns `HDR` if color primaries contain BT.2020 even when transfer is not PQ or HLG.

BT.2020 primaries alone do not prove HDR. BT.2020 SDR content is possible.

### Required change

Use transfer characteristics as the HDR decision source:

- PQ / SMPTE ST 2084 -> `HDR10` as the current generic PQ label;
- HLG -> `HLG`;
- otherwise -> no HDR label.

Do not label content HDR solely because primaries are BT.2020.

Keep wide-gamut/color-primaries information separately in `PortVideoInfo.colorPrimaries`.

### Required tests

Add:

- PQ + BT.2020 -> HDR10;
- HLG + BT.2020 -> HLG;
- BT.2020 + SDR/BT.1886 transfer -> no HDR label;
- BT.709 SDR -> no HDR label.

Do not infer native HDR output from this metadata label.

## 5. Required correction D — Architecture guard ignore rule is too broad

### Finding

The validation fix correctly stopped generated `.test` output from being scanned.

However the current walker ignores any directory named:

- `.test`
- `build`
- `oh_modules`

at any recursion depth.

That could accidentally hide a real source folder named `build`.

### Required change

Prefer scanning explicit source roots, especially:

```text
linkora_core/src/main/ets
```

instead of recursively scanning the entire module and excluding arbitrary directory names.

For other checks, likewise prefer known production source roots.

Generated outputs may be ignored, but production source must never be skipped merely because one ancestor directory happens to be named `build`.

### Required tests

Keep/add controlled fixture checks:

- platform import under generated `.test` is ignored;
- the same platform import under `linkora_core/src/main/ets` fails;
- implementation import under core production source fails.
