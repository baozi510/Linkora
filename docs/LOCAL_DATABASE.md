# 本地数据库

## 定位

Linkora 使用 HarmonyOS 关系型数据库保存媒体索引、来源关系、最近播放和播放状态。数据库属于 entry 平台适配层；`linkora_core` 只声明仓储接口，不依赖 ArkData，因此 UI 重做或平台适配替换不会影响业务模型。

当前数据库名为 `linkora_local.db`，安全等级为 S2，并启用数据库加密。网络密码、Cookie、请求头和完整敏感 URL 不写入关系库；需要保留的网络定位信息由 Asset Store 保存，数据库只记录服务器元数据、不可逆主键和资产别名。

数据库 schema v7 为 `network_server` 增加 `credential_alias`。新增或修改服务器时，密码先写入 Asset Store，关系库中的旧 `password_value` 保持为空；加载旧记录时会自动迁移已有密码，迁移成功后立即清空旧字段。删除服务器时同步删除对应 Asset Store 资产。

## Schema v1

| 表 | 用途 |
| --- | --- |
| `media_entity` | 媒体逻辑实体及稳定身份键，不读取视频内容计算 Hash |
| `media_locator` | 实体在媒体库、手动选择来源或后续目录来源中的实际位置 |
| `media_collection` | 相册、手动选择集合和后续授权目录 |
| `collection_membership` | 位置与集合的成员关系，允许一个实体出现在多个目录或来源中 |
| `playback_state` | 播放位置、时长、完成状态和最近播放时间 |
| `recent_entry` | 最近打开列表，最多保留 12 条 |
| `scan_checkpoint` | 冷启动指纹、扫描代次和扫描状态 |

实体、位置和成员关系必须分离。当前媒体实体使用 `source_kind + locator` 作为稳定身份；同一系统媒体 URI 复用同一实体，不对视频文件做全量 Hash，也不自动合并两个独立副本。相册模式按 `collection_membership` 展示，视频模式按 `media_entity` 聚合。根库刷新只重建系统扫描得到的归属，单相册刷新只替换当前相册成员，因此一个视频被多个来源看到时不会丢失其他归属。这样手动选择的文件既可出现在“手动添加”根集合，也可保留它原来的相册归属。

## 当前接入状态

- 最近播放已经使用 `recent_entry`，重复打开同一来源只更新时间，不产生重复行。
- 播放书签已经使用 `playback_state`，同一来源的写入串行化，旧的异步结果不会覆盖更新结果。
- 媒体库索引、手动来源、最近播放和播放书签共用数据库级写队列，禁止多个仓储各自串行但在同一 `RdbStore` 上交叉进入事务。
- 少于 30 秒的媒体、开头 5 秒内不写入书签；播放完成或距结尾不足 30 秒时清理书签。
- 网络定位信息先写入 Asset Store，再把资产别名保存到 `recent_entry.locator_ref`。
- `PhotoAccessHelper` 的扫描结果已经通过 `LocalMediaIndexStore` 写入媒体实体、位置、用户相册、应用创建型相册和成员关系表；页面收到的是数据库回读结果。
- `DocumentViewPicker` 的多选结果写入 `source_kind = document_picker` 的虚拟集合；URI、展示名、大小、修改时间和授权状态可跨冷启动恢复。失效条目由用户显式移除或批量清理，应用不会据一次读取失败自动删除记录。
- 本地列表通过独立进度仓储批量关联 `playback_state`。播放身份仍由来源类型与 URI 生成，不读取文件内容计算 Hash；媒体库与手动入口指向同一 URI 时共享书签。
- 冷启动在确认媒体权限后先读取 `scan_checkpoint` 标记的最后一份完整快照并发布列表，再读取轻量系统指纹。指纹由媒体总数、最新资产和相册摘要组成；变化、探测失败或上次完整扫描超过 6 小时时才执行全量校准。快照的扫描代次与完成时间进入核心状态，校准失败时保留缓存和上次同步时间，不把暂时性错误解释成媒体被删除。
- 相册进入时采用 stale-while-revalidate：先从当前完整索引读取相册成员（空相册也视为有效命中），立即展示后再向系统媒体库校准该相册；校准失败时继续保留相册缓存。
- 全库和单相册刷新采用短事务，写入失败时回滚，并降级使用当次系统扫描结果，同时向页面发布“媒体索引未保存”的可恢复提示。
- 每次完整快照使用扫描代次删除失效位置、相册和孤立实体；系统查询分页执行，但不设置媒体条目总数上限。扫描前后指纹不同的结果不得清理旧数据。
- 已订阅系统媒体资产和相册变更通知；连续通知经过 300 ms 防抖，扫描期间发生的通知合并为下一次刷新，不并发启动扫描。适配器使用扫描代次阻止已被替代的结果进入数据库。
- 手动文件先在事务外以最多 3 路并发完成文件状态与媒体元数据读取，再用短事务写入。解析器失败只更新大小和修改时间，保留已有时长与分辨率；文件类型随 `media_type` 持久化，已覆盖视频、图片、音频和字幕。
- 文件选择授权按 50 条分批持久化，批量失败后逐条重试；移除记录时同步尝试撤销系统持久化读权限。手动来源每 6 小时最多验证一次。
- 全量校准若与当前快照内容完全一致，保留原媒体与相册数组引用，只更新同步状态和快照元数据，避免虚拟列表发生无意义重建。
- `scan_checkpoint` 已记录扫描代次和完成状态；目前变更通知触发安全的快照刷新，按变更 URI 精确查询的增量优化仍属于后续工作。

## 发布与升级规则

当前处于未发布开发阶段，不迁移旧 Preferences 测试数据。Schema v1 使用幂等建表语句建立基线；测试数据库可以直接清除后重建。

首次商用版本发布前必须冻结 v1。之后每次结构变化都必须：

1. 增加数据库版本号，禁止修改已经发布的旧版本建表语句。
2. 提供可重复执行的升级步骤，并覆盖从所有仍受支持版本升级的测试。
3. 升级失败时保留原数据库，不自动删除用户播放历史或授权来源。
4. 在真机上验证加密数据库、低存储空间、异常退出和跨版本升级。

## 查询与资源规则

- 所有业务值使用参数绑定，不拼接到 SQL。
- 每个 `ResultSet` 必须在 `finally` 中关闭。
- 页面不得直接执行 SQL；只能通过 entry 仓储实现访问。
- 应用外壳不等待媒体扫描完成；数据库缓存可用时直接展示。数据库异常时媒体索引降级为当次系统扫描结果，历史与进度降级为空，不能阻塞本地媒体浏览。
- 日志只记录阶段、数量和错误码，不输出 URI、URL、资产别名或凭据。

## 缓存有效性

- 只有 `scan_checkpoint.status = idle` 且存在有效 `completed_at` 的完整快照可以用于冷启动和相册缓存；异常退出留下的 `scanning` 快照不会展示。
- 冷启动先以轻量指纹验证缓存，命中时避免重复全量扫描；每 6 小时强制完整校准一次。运行期间的系统媒体变更通知与用户下拉刷新仍会触发校准，因此缓存不会被无限期当作权威数据。
- 只有完整扫描可以按代次删除过期记录；不完整结果不得清理旧数据。数据库写入失败时保留上一份完成快照，页面使用本次扫描结果作为临时降级。
- 缩略图加载器不共享可释放的 `PixelMap` 对象，而是保留最多 24 份原始像素 LRU；每个卡片从缓存创建独占 `PixelMap` 并自行释放。同一 URI 的并发读取合并为一个系统请求。磁盘缩略图缓存仍需独立的编码、配额和淘汰策略后再接入。
